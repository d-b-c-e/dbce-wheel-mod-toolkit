# Independent toolkit review — 5 September 2026

Reviewed checkout: `d170e0403aee67e4dd82685b87156377553e8ee1`, before the improvements described in subsequent commits. This extends the Cruis'n Collection assessment. It reviews source and automated tests; no physical force was applied and no consumer game was modified during this assessment.

The abstraction is heading in the right direction. Game sampling, force composition, force conditioning, device output and telemetry serialization are different responsibilities. Keeping game memory offsets and engine hooks in consumers is the correct boundary. The most valuable next step is to make those boundaries carry explicit validity, timing, identity and diagnostics. A reusable DLL alone cannot prevent a consumer from supplying stale speed, clipping away impacts, confusing a product ID with a device instance, or losing an effect on reconnect.

## What should remain shared

The toolkit should own the force math and its units, device lifecycle, capability discovery, calibration representation, effect allocation/update/recovery, diagnostics schema, packet layouts and transport. Consumers should own extraction from game state, interpretation of that game's collision flags, the decision that a race is active, and mapping between game units and the neutral contract. Templates should show that boundary with one concrete working adapter and a replayable sample trace.

Use an explicit adapter capability declaration: native motor signal, vehicle speed, lateral acceleration, tire force, collision event, steering input, brake and throttle. Each supplied value should carry a sample time and a status such as valid, stale, unavailable or estimated. A field's source should identify whether it is native game state, OCR, differentiated data or synthesis. Unsupported signals should stay unsupported rather than acquiring plausible defaults.

The native C ABI and managed facade should expose equivalent logical operations. A process should own one device session; session state should distinguish discovered, selected, acquiring, active, lost and closed. Device gain/direction/axis are properties of the selected wheel profile, while the game's force tune is a separate profile. A user tuning a Moza should not unknowingly change a game's collision classifier for everyone else.

DirectInput and SDL should implement the same desired-effect contract before being judged interchangeable. The current native implementation is DirectInput; the SDL backend in the roadmap is still planned. Cruis'n uses its own SDL worker. Importing the shared shaper did not import the toolkit's effect lifecycle or diagnostics. Do not claim backend equivalence based on equal input numbers: axis, waveform frequency, duration, update/start semantics and device gain all matter.

## Define “good FFB” as measurable properties plus a recorded preference

A single “feels good” scalar is not a useful acceptance target. Store objective measurements and subjective judgments separately:

- Source-to-output timing, p50/p95/p99 latency, longest unserviced interval and watchdog release time.
- Time spent clipped, steady steering headroom, event peak and integrated event area, smoothing response, sign around center, and net directional bias.
- Event recognition precision/recall against **labeled** collisions, rough surfaces and ordinary corners. A large force rise is only a proxy; one driver's trace cannot establish universal thresholds.
- Effect creation/update/start/reacquire failures, device identity, selected axis and requested versus acknowledged effects.
- A short paired driving evaluation of road feel, steering resistance, impact distinctness, chatter and fatigue, with wheel model/firmware/rotation/base settings recorded.

Use several wheel families, not just this R12: gear-driven Logitech, belt-driven hardware and at least two direct-drive vendors. Different wheel bases have different friction, bandwidth and saturation. Publish which profiles have actually been tested, on which devices. A tune passing numerical conformance is a stable algorithm, not a certified physical experience.

## A testing architecture that carries fixes across projects

Keep the current C++/C# conformance vectors; they are valuable protection against accidental divergence. Add semantic tests whose expected outcomes come from invariants rather than a regenerated dump: an unknown-direction impact at center is nonzero; a pulse has a bounded lifetime; device strength zero means zero across all effects; a stale sample releases the force; a failed explicit selection never activates another wheel. Test at several fixed rates and with jitter, gaps and reordered samples.

Replay captured **source signals** through the model, then record each stage: native input, normalized input, structural force, event contribution, conditioned output, gain, saturation and backend acknowledgement. Preserve the source revision/profile hashes and the wheel profile. Do not regenerate reference outputs automatically on a passing test. A changed golden file requires a reviewed explanation of the changed behavior.

For device lifecycle testing, place a fake DirectInput/SDL implementation behind the device adapter. Script loss of acquisition, creation failure, failure after a previously successful Start, disconnect, reconnect with a different enumeration index and window teardown. The test asserts zero/release/recreate order and timeout behavior without a powered wheel. Physical smoke tests remain necessary for ABI and firmware behavior, but should not be the only way to exercise error paths.

Cruis'n's input recorder belongs in its MAME adapter: INP knows the emulator's analog interpolation and clock. The toolkit should standardize the case manifest and signal traces rather than attempt to replay every game's raw input with one clock. Unity/Unreal/native ports can provide different recorders that produce the same provenance and diagnostic conventions. Preserve the whole driving prefix and analyze a selected interval; starting in the middle can change RNG, AI, streaming or collision state.

Run managed tests and pure native conformance in CI on each change. Include MSVC and MinGW because consumers compile the same headers using both. Check x86/x64 export parity when the DLL changes. Package only after all required checks pass. Add a consumer matrix that builds narrow adapter probes from each actual pin, avoiding a requirement to install every game in CI.

## Adoption sequence

1. Repair the currently failing profile reference and put the existing suites in CI. Register Cruis'n as a real consumer.
2. Fix centered impacts and selection ambiguity with semantic regression tests. Add shared waveform-event detection and a trace-based evaluation tool; do not silently change every game's tune.
3. Add signal validity/timing/provenance, then use it in one native adapter and one managed adapter. Retain Forza as an export format, not the canonical internal state model.
4. Add a fake device backend and lifecycle contract before consolidating Cruis'n's SDL worker. Make backend limitations visible instead of silently falling back to a different effect or wheel.
5. Ship a minimal new-game template with a diagnostic trace, deterministic signal replay, capability declaration and explicit “no speed / no collision source yet” states. This is a better starting point than another copied input hook with a working-looking dashboard.

The first implementation work should be small, testable shared components with explicit consumer pin bumps. Replacing every consumer at once would make it harder to identify whether a regression came from game sampling, shared math or device output.
